### 1.1 还需补写进契约的三条边界口径（任务单 §〇）

现状实现是 `next_unlock() = max(prev_unlocked, min(consecutive_fail // 2, 4))`；

**顺带修掉的一处工具缺陷（同属「不得静默丢弃」）**：

**根因（实测复现，非推断）**：产品侧多处用的是 `with connect() as conn:`

**探针结论**：读一次接口后直接 `rmtree` ⇒ `PermissionError`；同场景先 `gc.collect()` ⇒ `OK`。
**修法**：验收脚本**不改产品代码**，只在清理前 `gc.collect()`（最多重试 3 次）；

> **不是连接生命周期的修复**。根因仍在产品侧调用点用 `with connect() as conn:`
> —— 它只提交／回滚、**不关连接**。「连跑 6 次成功」**不保证以后都不会占用文件**。
> 后续应对相关连接采用**明确关闭**（`log_isolation_run()` 已是此写法，其余调用点未逐一审计）；

#### 二、身份绑定与数据分离（当前仍是缺口）

- **编号框是自由文本**：`participant_id` 由前端直接提交，**无登录／无一次性凭证**，
  同一编号在不同设备上会**接续同一份历史记录**（`error_memory` 与 `submit_seq` 都按 `participant_id` 累计）。
- **正式实验前必须补**：① 唯一编号分配；② 用登录或一次性凭证**绑定编号**，避免串号；
  ③ **姓名与编号对应表单独保管**，不放进学生可访问接口。
- **演示数据与实验数据必须分开**：本机真实库 `pedagogy.sqlite` 当前 `submission_log` **40 行**，
  其中**多数是测试/调试痕迹**（`T_E2E_1..6`、`TEST_SPY`、`UICHECK`、`DRILL_API`，以及 `S01` 的 26 行手测）。
  本轮导出工具已提供 `--exclude-participant`（可重复）用于**按被试排除**，
  但**正式实验仍应使用独立数据库或明确的实验批次标识**，**不靠事后猜测哪些记录属于测试**。
- **未做**：本轮**未**改动身份入口、**未**引入登录、**未**迁移或清理任何真实库记录。

#### 三、数据交付：管理员离线导出与一致性备份（本轮已实现）

**新建 `tools/export_experiment_data.py`**（离线、只读、不启动学生进程、不联网、不 import `app.db`）：

- **全部 CSV、全部对账数字、`--backup` 交付的备份都取自同一份快照**（按评阅 m02810 第 1 点修）：
  先用 SQLite 在线备份 API 把源库备份到**本次运行独占的临时目录**，此后所有查询只读这份快照，
  `--backup` 交付的**就是这一份快照文件**。先前版本「先查三份内容、再查行数、关连接、另开连接备份」
  在并发写入下会拿到**不同时刻**的数据（在线备份只保证备份自身一致，**不会**让先前查询与它一致；
  **再对源库备份一次同样不行** —— 那是第二次读源库）。
- **源库与输出目标不得重合**（按评阅 m02810 第 2 点修）：比对 `resolve()` 后的绝对路径，
  覆盖「备份＝源库」「CSV＝源库」「备份＝某个 CSV」三种情形；**`--force` 只能覆盖旧导出物，
  不得绕过源库保护**。原先只判「文件是否存在」，而「源连接只读」挡不住后续的文件写入。
- **文本单元格防公式**（按评阅 m02810 第 3 点修）：以 `= + - @`／制表符／回车开头的**文本**加前导单引号，
  数值不受影响；**引号转义挡不住公式解释**，必须改写单元格文本本身。转换规则会打印出来。
- **先对账、后报成功**：全部对账通过后才打印成功结论；**失败不把不完整产物当完整导出**。
- 退出码：`0` 成功／`1` 错误／`2` 拒绝继续（库不存在、表缺失、路径重合、文件已存在）。

#### 四、记录能力核对：哪些统计做得了、哪些做不了（**不假定现有日志已包含**）

| 想分析的 | 现在能否支撑 | 口径与限制 |

**`glm-5.3-flash` 未采用**——不是「更差」，而是它在 L1/L4 **首次**就产出代码（须靠重试兜回），
属于「分类更准、但提示更易越界」的取舍；**若将来更看重分类准确率，可重新评估**。

**共性问题（与选型无关，另行观察）**：`deepseek-flash` 与 `step-3.7-flash` 都在
`ParserError: 无法解析输入格式` 一条上给出**不合法知识点**（67%）。这更像**同一提示词／同类边界样例的共性**，
不是某模型独有缺陷，**待真实判题接通后再查**。

#### 二、思考强度参数（`reasoning_effort`）

**实现（`app/llm.py`）**：新增 `PH_LLM_REASONING_EFFORT` 覆盖入口；`_reasoning_effort()`
返回 `None` 时**完全不发送**该参数。

**关键兼容性事实（已实测核对，非推断）**：`reasoning_effort` 在 openai SDK
**1.60.0** 才进入 `chat.completions.create()` 签名；**1.30.0／1.40.0／1.50.0／1.55.0
均无该参数，也没有 `**kwargs` 兜底**（解包 wheel 逐一核对）⇒ 旧版传了会 `TypeError`。
而 `requirements.txt` 声明的是 **`openai>=1.30`**，故 **`DEFAULT_REASONING_EFFORT` 定为空串
（默认不发送）**，由本机 `.env` 显式选 `none`。本机实际安装为 `openai 3.31.0`，支持该参数。

> ⚠️ **兼容性边界（部署说明，勿省略）**：「默认不发送」解决的是**旧配置下的兼容**，
> **不是「启用参数后也兼容」**。另一台机器若装的是依赖范围允许的旧版 SDK（1.30–1.55），
> **即使只设 `PH_LLM_REASONING_EFFORT=none` 也会因不支持该参数而报错**。
> ⇒ 口径：**未配置时兼容原调用方式；显式启用该参数时，必须使用经验证支持它的
> SDK 与服务端组合。**

> ⚠️ **另需注意**：「签名里有该参数」**不等于**该版本正式支持 `"none"` 这个取值，
> 也**不等于**中转站会执行它。目前的在线观察只支持
> **「当前安装版本（openai 3.31.0）＋当前中转站」**这一组合，
> **不能外推到所有 `>=1.60` 的版本或别的中转站**；换机部署时须一并记录版本并复核。

**已观察到的事实（限定范围）**：在**当前中转站、当前模型别名**下，对本批**分类请求**
发送 `reasoning_effort="none"` 时延迟较低（均值 1133ms vs 不发送 1821ms，n=12），
且返回的 reasoning 字段为空。
**不能外推为**：① 所有提示任务都稳定快约 38%；② reasoning 字段为空即证明服务内部完全没有推理；
③ 不发送参数等于「开启思考」——**不发送只是采用服务端默认行为**。

**质量证据如实登记为「方向不一致、不足以判断」**：L4 首次规则通过率
n=10 为 10/10 vs 7/10，n=3 时为 33% vs 100%，**两批数字都保留**。
**首次通过防泄规则 ≠ 提示正确、分级合理或对学生有帮助**，故**不以规则通过率作为教学质量优劣的证据**。
本轮的换用理由**仅为延迟收益**，教学质量维度待真实判题接通后用固定样例审核。

#### 实现中踩到的四个坑（都已修正，写在这里避免重犯）

1. **`Add-Content` 与 cmd 的 `>>` 抢同一个文件** ⇒ `The process cannot access the file ... because it is being used by another process`。
   修正：**日志分工**——`server.log` 只由 cmd 重定向写，启动器只写 `launcher.log`。
2. **`RedirectStandardOutput` 的父进程一退出，读端就关** ⇒ uvicorn 写日志会撞 `BROKEN_PIPE` 直接退出；
   而若父进程阻塞在 `WaitForExit`，PowerShell 的异步事件又不派发，日志照样写不进去。
   修正：**改用 cmd 的文件级重定向**，两个问题一起没有。
3. **`Popup($msg, 0, ...)` 的第二个参数 0 表示"永不自动关闭"** ⇒ 弹窗进程一直挂着。
   修正：错误提示统一给 **15 秒自动关闭**。
4. **PowerShell 5.1 读 `.ps1` 依赖 BOM 判断编码**，无 BOM 时中文注释会被按 ANSI 解释并可能报错。
   修正：两个 ps1 都**以 UTF-8 带 BOM 保存**（VBS 则相反，必须纯 ASCII）。

### 6.1 决策汇总

| 议题 | 定案 |
|---|---|
| **Q1** 提示入口是否判题 | **允许判题**（保留"针对学生当前代码给提示"的能力）。**不维护单独的累计数字**，改为**每次实际判题留执行事件**（`execution_id`／来源＝正式提交或纯提示／起止／耗时／状态／关联 ID），由事件统计执行次数。**提交次数、提示请求次数、判题执行次数三者分开表述，不得混成一个"尝试次数"** |
| **Q2** 异常一致性 | **b 为主 + a 为辅**：判题事实**及时持久化**，组件对**可预期的模型异常**受控降级。**判题事实与模型反馈的可靠性不得捆绑** |
| **Q3** 无围栏防泄 | **分级检测**，但**按各等级"允许内容"定义**，不是"L1–L3 从严、L4 从宽"的粗口径。**L3 的伪代码不得仅因缩进/循环词/代码外观被拦** |
| **Q4** 隐藏用例报错 | **接受为保护隐藏数据牺牲部分诊断细节**：只给判题状态、`error_type`、**受控提取的异常类别名**（如 `ZeroDivisionError`）+ 服务端固定说明。**不透传冒号后原始消息、原始输出、traceback** |
| **Q5** 前后测分类 | **允许本地规则分类用于内部实验记录**，但**不向学生返回教学诊断**、**不更新错误记忆**、**不调用模型**。**不能只让前端不显示而 API 仍返回教学字段** |
| **Q6** 新增事件表 | **属受控增量契约修订**（不改旧 16 列语义）。须登记：表结构与事件语义、与提交表的关联方式、哪些入口写入、重试/失败/禁用如何记录、是否影响原响应、保留与删除规则、幂等迁移与旧库兼容 |
| **Q7** 连败窗口 | **暂不扩大改造**。真正瓶颈**不是窗口（10 行够表达 10 连败），而是写死的 4 级上限**。契约须写明：窗口只做**有界连败**、**级数上限硬编码为 4**；如需精确连败指标再另算 |
| **Q8** 运营事项 | **与算法决策解耦**，分别处理（见 6.5） |

### 6.2 Q2 的四条硬约束（不得违反）

1. **旧 16 列语义不动**，处理状态放**关联事件表**
2. **不让默认值冒充处理成功**——"未分类"要能区分"规则真没命中"与"分类服务失败"
3. **事务保持短**，**不把模型网络调用包进长事务**；记忆更新与处理状态须一致，**重试不得重复加次数**
4. **本轮不做自动续跑**；且**不得把所有异常吞掉装成功**——只对可预期模型超时降级，**数据库写入失败与程序缺陷必须暴露**

> **关联表是这套设计的解药**：判题事实落库时教学几列必然先填默认值，
> 读日志者先看关联表状态——`未完成` → 默认值只代表"还没跑"；`完成` → 才代表"真的没命中"；`失败` → 教学反馈失败但判题事实有效。
> 本轮**只做"判题完成后立即落事实"**，不做"接收请求即落一行"（后者需引入"判题未开始"的行语义，投入产出不划算）。

### 6.4 架构连带：三种记录合并为**一张事件表**

| 事件类型 | 写入方 | 承载 |
|---|---|---|
| 执行事件 | 判题层 | 来源（提交／纯提示）、起止、耗时、状态、关联 ID |
| 提示事件 | 提示层 | 请求、结果（成功／阶段禁用／生成失败）、返回等级、生成来源（`llm`／`llm_retry`／`fallback`） |
| 处理状态 | 管线 | 本次提交的教学处理：未完成／完成／部分失败／失败 |

**最低限度契约要求（定表时逐条落实）：**

1. **`event_type` 必须区分三类事件**：`execution`（执行）／`hint`（提示）／`teaching`（教学处理）。
   三类**不得混成一条含义模糊的记录**。
2. **每条事件有自己的 ID**；**同一请求使用共同关联 ID**（`request_id`）。
3. **能关联提交记录**（`submission_id`）；**纯提示没有提交记录时允许为空**——
   不得为凑关联而给纯提示补写提交行。
4. **每类事件各自定义状态**，**不得把"判题完成"与"提示成功"混为一谈**
   （执行状态／提示状态／教学处理状态互不覆盖）。
5. **执行事件的写入时机**：判题**实际开始前**先写一行 `started`，**结束后更新**为终态。
   → 这样无需在提交表里引入"判题尚未开始"的行语义，
   也能留下"**执行已启动但中途终止**"的痕迹。
   → 若为省事**只写终态**，则**必须明确：统计的是"已记录的完成执行"，
   不是所有已启动执行**（评阅方更建议前一种，两者都可接受，但口径不能含糊）。
6. **保存提交事实与创建对应"教学未完成"状态，放在同一个短事务里**——
   否则会出现"提交行存在、关联状态不存在"的空档，无法对账。
   （这条与 6.2 的"事务保持短、不把模型网络调用包进长事务"**不冲突**：
   这里只包两次本地写库。）

**落地顺序因此为：**

1. **D 单独修复**（按入口区分记忆写入与连败计算，**不碰事件表**）→
   可先独立验收，**不被新表设计拖住**；
2. **统一确定事件表契约**（C 与 I 共用一张表）；
3. **实现 Q1／C／I**（执行留痕、提示事件、提交处理一致性）；
4. 按计划推进 **F、B**。

**不得为 C 与 I 各造一套记录机制。**

> 另注：Q1 要求两个入口**共用同一套安全隔离、并发限制与超时策略**——
> **提示不计提交次数 ≠ 提示可无限消耗执行资源**。
