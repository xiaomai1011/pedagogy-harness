### 1.1 还需补写进契约的三条边界口径（任务单 §〇）

现状实现是 `next_unlock() = max(prev_unlocked, min(consecutive_fail // 2, 4))`；
未请求时展示恒为 `0`；请求时 `unlocked = max(unlocked, 1)` 再原样展示。

1. **L1 保底＝"把解锁上限一并抬到 L1"（保底解锁）**，不是"展示越过解锁上限"。
2. **纯提示请求不得抬高解锁等级**；**"连续失败次数"含本次提交**——两条都要写进契约并加测试守住。
3. **解锁上限作用域＝"被试＋题目"**：同题内由日志单调保持、通过后不回退；
   **换题**从该题自身历史重算（跨题共享的是**错误记忆**，不是解锁上限）。

### 1.3 三处验收／措辞修正（评阅提出，已核验成立）

1. **L1 保底是唯一例外**：`next_state` 请求分支有 `unlocked = max(unlocked, 1)`，
   且该值在**提交入口会落库**（`hint_unlocked_level`）、在**提示入口不落库**。
   → 口径应写成"**除 L1 保底外**，纯提示请求不改变解锁上限"，
   并明确"**保底是否持久化按入口区分**"。
2. **H 的混排用例不能一律拦**：合规的 L4 局部片段本就可能与解释文字混排
   → 改为"混排内容**包含完整解法或超出等级边界**才拦"。
   （这是修正验收条件，**不是**放宽防泄目标。）
3. **提示正文拆分不是纯前端工作**：[hint_ladder.py:154](file:///D:/Downloads/Trae-workspace/pedagogy-harness/app/harness/hint_ladder.py#L154)
   把判题反馈与提示正文拼成同一个 `message` 字符串
   → 可靠拆分需**后端先补响应字段**，不得让前端按固定句子／换行数去猜。
   （这只是 API 展示字段拆分，**不冲突**于已否决的"结构化字段输出"防泄路线。）
