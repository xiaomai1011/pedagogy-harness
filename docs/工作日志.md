### 1.1 还需补写进契约的三条边界口径（任务单 §〇）

现状实现是 `next_unlock() = max(prev_unlocked, min(consecutive_fail // 2, 4))`；
未请求时展示恒为 `0`；请求时 `unlocked = max(unlocked, 1)` 再原样展示。

1. **L1 保底＝"把解锁上限一并抬到 L1"（保底解锁）**，不是"展示越过解锁上限"。
2. **纯提示请求不得抬高解锁等级**；**"连续失败次数"含本次提交**——两条都要写进契约并加测试守住。
3. **解锁上限作用域＝"被试＋题目"**：同题内由日志单调保持、通过后不回退；
   **换题**从该题自身历史重算（跨题共享的是**错误记忆**，不是解锁上限）。

| **Q1** 提示入口是否判题 | **允许判题**（保留"针对学生当前代码给提示"的能力）。**不维护单独的累计数字**，改为**每次实际判题留执行事件**（`execution_id`／来源＝正式提交或纯提示／起止／耗时／状态／关联 ID），由事件统计执行次数。**提交次数、提示请求次数、判题执行次数三者分开表述，不得混成一个"尝试次数"** |
| **Q2** 异常一致性 | **b 为主 + a 为辅**：判题事实**及时持久化**，组件对**可预期的模型异常**受控降级。**判题事实与模型反馈的可靠性不得捆绑** |
| **Q3** 无围栏防泄 | **分级检测**，但**按各等级"允许内容"定义**，不是"L1–L3 从严、L4 从宽"的粗口径。**L3 的伪代码不得仅因缩进/循环词/代码外观被拦** |
| **Q4** 隐藏用例报错 | **接受为保护隐藏数据牺牲部分诊断细节**：只给判题状态、`error_type`、**受控提取的异常类别名**（如 `ZeroDivisionError`）+ 服务端固定说明。**不透传冒号后原始消息、原始输出、traceback** |
| **Q5** 前后测分类 | **允许本地规则分类用于内部实验记录**，但**不向学生返回教学诊断**、**不更新错误记忆**、**不调用模型**。**不能只让前端不显示而 API 仍返回教学字段** |
| **Q6** 新增事件表 | **属受控增量契约修订**（不改旧 16 列语义）。须登记：表结构与事件语义、与提交表的关联方式、哪些入口写入、重试/失败/禁用如何记录、是否影响原响应、保留与删除规则、幂等迁移与旧库兼容 |
| **Q7** 连败窗口 | **暂不扩大改造**。真正瓶颈**不是窗口（10 行够表达 10 连败），而是写死的 4 级上限**。契约须写明：窗口只做**有界连败**、**级数上限硬编码为 4**；如需精确连败指标再另算 |
| **Q8** 运营事项 | **与算法决策解耦**，分别处理（见 6.5） |

### 6.2 Q2 的四条硬约束（不得违反）

1. **旧 16 列语义不动**，处理状态放**关联事件表**
2. **不让默认值冒充处理成功**——"未分类"要能区分"规则真没命中"与"分类服务失败"
3. **事务保持短**，**不把模型网络调用包进长事务**；记忆更新与处理状态须一致，**重试不得重复加次数**
4. **本轮不做自动续跑**；且**不得把所有异常吞掉装成功**——只对可预期模型超时降级，**数据库写入失败与程序缺陷必须暴露**

> **关联表是这套设计的解药**：判题事实落库时教学几列必然先填默认值，
> 读日志者先看关联表状态——`未完成` → 默认值只代表"还没跑"；`完成` → 才代表"真的没命中"；`失败` → 教学反馈失败但判题事实有效。
> 本轮**只做"判题完成后立即落事实"**，不做"接收请求即落一行"（后者需引入"判题未开始"的行语义，投入产出不划算）。

### 6.4 架构连带：三种记录合并为**一张事件表**

| 事件类型 | 写入方 | 承载 |
|---|---|---|
| 执行事件 | 判题层 | 来源（提交／纯提示）、起止、耗时、状态、关联 ID |
| 提示事件 | 提示层 | 请求、结果（成功／阶段禁用／生成失败）、返回等级、生成来源（`llm`／`llm_retry`／`fallback`） |
| 处理状态 | 管线 | 本次提交的教学处理：未完成／完成／部分失败／失败 |

**最低限度契约要求（定表时逐条落实）：**

1. **`event_type` 必须区分三类事件**：`execution`（执行）／`hint`（提示）／`teaching`（教学处理）。
   三类**不得混成一条含义模糊的记录**。
2. **每条事件有自己的 ID**；**同一请求使用共同关联 ID**（`request_id`）。
3. **能关联提交记录**（`submission_id`）；**纯提示没有提交记录时允许为空**——
   不得为凑关联而给纯提示补写提交行。
4. **每类事件各自定义状态**，**不得把"判题完成"与"提示成功"混为一谈**
   （执行状态／提示状态／教学处理状态互不覆盖）。
5. **执行事件的写入时机**：判题**实际开始前**先写一行 `started`，**结束后更新**为终态。
   → 这样无需在提交表里引入"判题尚未开始"的行语义，
   也能留下"**执行已启动但中途终止**"的痕迹。
   → 若为省事**只写终态**，则**必须明确：统计的是"已记录的完成执行"，
   不是所有已启动执行**（评阅方更建议前一种，两者都可接受，但口径不能含糊）。
6. **保存提交事实与创建对应"教学未完成"状态，放在同一个短事务里**——
   否则会出现"提交行存在、关联状态不存在"的空档，无法对账。
   （这条与 6.2 的"事务保持短、不把模型网络调用包进长事务"**不冲突**：
   这里只包两次本地写库。）

**落地顺序因此为：**

1. **D 单独修复**（按入口区分记忆写入与连败计算，**不碰事件表**）→
   可先独立验收，**不被新表设计拖住**；
2. **统一确定事件表契约**（C 与 I 共用一张表）；
3. **实现 Q1／C／I**（执行留痕、提示事件、提交处理一致性）；
4. 按计划推进 **F、B**。

**不得为 C 与 I 各造一套记录机制。**

> 另注：Q1 要求两个入口**共用同一套安全隔离、并发限制与超时策略**——
> **提示不计提交次数 ≠ 提示可无限消耗执行资源**。
