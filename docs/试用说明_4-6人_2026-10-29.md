# 小规模试用说明（4–6 人）

日期：2026-10-29　适用版本：`0.5.2-enroll` 及之后
定位：**工程验证＋小规模试用＋探索性描述分析**，不用于证明因果教学效果或各组件的独立贡献。

> 拟由 4–6 名未参与技术开发的同学完成小规模试用，保留前测—练习—后测流程，以描述性分析考察流程可行性、使用体验及观察到的学习表现变化，不用于证明因果教学效果或各组件的独立贡献。

本文只记录**本次规模调整**与现场怎么用；历史验收报告与日志不回头改写，只在其末尾补一条日期说明。

## 二、本次的四处调整

1. **人数**：4–6 人，写进说明与名单，**不写进代码**；编号按实际登记顺序生成。
2. **身份**：一人一机，用**机器自动登记**——学生第一次打开页面时服务端分配 `A00x`，先认 Cookie，Cookie 丢失按来源地址找回，所以刷新、重开、清 Cookie 都是同一个号。
   - 姓名 ↔ 编号对照表由**负责人**单独保存，不进仓库、不放进普通导出。
   - 开发自检、验收用的 `A001–A009`（含 `TEST-101`、`T002`、`S01`）都不是试用参与者，导出时用 `sqlite3` 只读删除或另存副本，再在分析前把它们从 CSV 里剔除（分析脚本本身不猜测谁不是参与者）。
3. **题目**：由负责人从现有题库确定**前测 3 题、练习 6–8 题、后测 3 题**，用管理台「发题」只发布这一套；其余题目保留在题库中不删除。阶段仍由服务端按题目 `phase` + 批次控制。
4. **批次与库**：建议新建 `TRIAL-20261029` 批次与独立库 `data/experiment_trial_20261029.sqlite`。
   - 预留的 `data/experiment_formal_20261028.sqlite` 经核对**不是空库**（有 `S01` 的 4 条提交、22 条事件），按“不删记录清库”的要求不改用它；
   - 验收库 `data/experiment_acceptance_20261028.sqlite` 继续只作验收；
   - 切换库与批次需要负责人在启动确认时拍板，**本轮未切换**。

## 三、现场流程（一人一机）

1. **开桌前**：打开管理台 `http://<主机>:8010/admin` →「电脑编号」→「复制登记表」，存一份初始名单。
2. **每人一台机器**：学生打开页面，顶部显示「身份：已登记 A00x」；把这个编号和机器位置记进名单。
3. **做题**：前测 3 题（无 AI）→ 练习 6–8 题（有提示）→ 后测 3 题（无 AI）→ 线下收集简短反馈。
4. **收尾**：先由负责人把题单存成 `docs/trial_plan_20261029.json`（练习只放选定的 6–8 题）：

   ```json
   {"pretest": ["S001", "S002", "S003"],
    "practice": ["P001", "P002", "P003", "P004", "P005", "P006"],
    "posttest": ["S004", "S005", "S006"]}
   ```

   然后导出并分析：

   ```
   python tools/export_experiment_data.py --db data/experiment_trial_20261029.sqlite \
       --out docs/exports/trial_20261029 --backup data/backups/trial_20261029.sqlite
   python tools/analyze_trial.py --export docs/exports/trial_20261029 \
       --plan docs/trial_plan_20261029.json --rule any
   ```
   得到：`participants_phases.csv`、`submissions.csv`、`hint_events.csv`、`trial_participants.csv`、`trial_summary.md` 与一份一致性备份。

## 四、分析口径（写报告时必须照此表述）

- **得分按题目计**：`passed_any`（至少通过一次）/`passed_first`（首次提交即通过）；**不是**通过提交次数。
- 题单与计分规则在开桌前固定，写进 `trial_plan_20261029.json`，试用中不改。
- `judge_ms`＝判题执行耗时；`model_ms`＝模型调用耗时；**都不是**学生作答时间。
- `gap_median_s` / `gap_mean_s`＝「提示 → 下一次提交」的间隔，含阅读、改码与操作，不能叫“思考时间”。
- **没有下一次提交的提示**单列 `pending_hints`，不当作失败、也不静默剔除。
- 未提交的题目进 `*_missing`，提交了没通过的进 `*_unfinished`；不补造、不只挑完成者。
- 任何百分比都写成「分子/分母」，例如 `4/5`；4–6 人时不做显著性检验。

## 五、已知缺口（本轮不扩平台）

1. **执行事件明细不在三份 CSV 里**：判题尝试/中止/无终态要看 `event_log` 的 `execution` 事件；库里有，导出没有单列。
2. **提示正文**保存在 `hint_state.last_response`，可按人按题回看，但没有单独的导出文件。
3. **错误记忆**有表（`error_memory`），管理台暂无页面；需要时用 SQL 或补一个只读查询。
4. 反馈问卷不建页面，由负责人线下收集。

以上四项都不影响本次试用出数：第 1、3 项需要时用 `sqlite3` 只读查询补一份说明即可。

## 六、负责人需要提供

1. 4–6 人名单（姓名 ↔ 匿名编号由负责人保存）；
2. 前测 / 练习 / 后测的**具体题号与顺序**（练习 6–8 题）；
3. 评分规则（按题计分，`any` 还是 `first`）与时间安排；
4. 试用窗口（开始/结束时间）与知情同意、数据保存期限；
5. 启动确认：版本、正式库/试用库路径、批次、身份模式、单实例、VM 就绪、备份位置。
